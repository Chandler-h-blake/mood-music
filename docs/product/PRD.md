# MoodMusic 首版产品需求文档

## 1 产品结论

MoodMusic 首版是一个个人自用、优先在 Windows 本机运行的 AI 选歌产品。它使用用户手动提供并由本机安全存储保护的 QQ 音乐 Cookie，同步当前账号的“喜欢”列表；再通过自然语言理解用户当下想听的整体感觉，只从该列表生成主候选队列，并通过 QQ 音乐网页版播放连接器完成最终播放。网络相似歌曲属于独立的发现功能，不得自动混入主结果。

首版要求完成端到端业务闭环。实施阶段可以逐步交付和验收，但只有全部发布门槛通过后才称为首个可用版本。

## 2 用户问题

### 2.1 背景

用户长期收藏了一千多首听起来顺耳的歌曲，但不同歌曲适合不同情绪、活动和环境。传统语言、流派和年代筛选无法准确表达“凌晨开车，有一点孤独，但不要太悲伤”或“有律动、适合当前跑步步频，但不要过分亢奋”这类整体感受。

### 2.2 核心任务

当用户产生某种听歌感觉时，系统应帮助用户：

1. 用一句自然语言表达需求。
2. 在自己的“喜欢”中找出全部真正符合整体感觉的歌曲。
3. 预览并调整顺序，而不是直接覆盖当前播放状态。
4. 确认后连续播放，并在队列结束时停止。
5. 必要时在独立区域发现库外相似歌曲。

## 3 目标与非目标

### 3.1 首版目标

- 建立字段完整、来源可追溯、允许未知值的歌曲画像体系。
- 支持用户手动粘贴 QQ 音乐 Cookie，由本机后端验证并分页同步完整“喜欢”列表，同时提供人工导入回退。
- 正确理解自然语言中的核心感觉、程度、排除项、场景和顺序趋势。
- 全量评估已完成画像的喜欢歌曲，返回全部通过均衡匹配标准的歌曲。
- 支持匹配度、情绪曲线和随机三种排序。
- 通过浏览器扩展将确认队列交给 QQ 音乐网页版，并在最后一首结束后停止。
- 将外部歌曲发现与主候选严格隔离。
- 对模型密钥、QQ 音乐 Cookie、日志和音频建立明确安全边界。

### 3.2 首版非目标

- 不提供多用户、社交、关注、评论或商业订阅。
- 不直接播放、下载、代理或缓存 QQ 音乐受保护音频。
- 不绕过会员、地区、版权、登录或 DRM 限制。
- 不修改、注入或重新分发 QQ 音乐桌面客户端文件。
- 不承诺跨所有 QQ 音乐版本和浏览器永久兼容。
- 不用一次跳过核心能力的“大模型调用”替代可审计的检索和边界校验。

## 4 产品原则

### 4.1 喜欢列表是唯一主候选来源

每次 AI 选歌都严格限定在当前“喜欢”成员集合内。队列提交前再次校验集合成员关系和可播放状态，防止同步变化或外部结果误入。

### 4.2 整体感觉优先

用户不需要操作标签表单。系统应把描述转换成内部语义意图，包括核心感觉、强弱、排除项、使用场景、节奏需求和排序趋势，但这些内部字段不应变成用户必须填写的筛选表。

### 4.3 未知比捏造更好

画像的字段结构在首次初始化时必须完整建立，但缺少可靠证据的字段保持 `unknown`。BPM、步频适配、语言、版本和风格等信息不得仅凭模型记忆伪造。

### 4.4 结果可以为空

没有歌曲达到标准时显示 0 首。系统不得自动放宽边界、塞入“最接近”的歌曲或把外部建议加入主候选。

## 5 核心用户流程

### 5.1 首次设置

1. 用户打开设置页，选择聊天模型、向量模型和可选的外部搜索提供方。
2. 用户将 API Key 写入本机操作系统凭据存储；应用数据库不保存明文密钥。
3. 用户在 QQ 音乐网页版正常登录，从浏览器开发者工具复制 Cookie，并粘贴到本机设置页；MoodMusic 不接收 QQ 密码。
4. 后端把 Cookie 写入 Windows 凭据存储或 DPAPI 保护的等价存储，完成登录验证后只显示去敏账号与有效状态。
5. 用户同步“喜欢”列表，后端通过只读 QQ 音乐适配器分页获取数据，系统展示已发现、已去重、新增、取消喜欢和失败数量。
6. 画像任务开始，界面持续显示进度、预计剩余项、暂停、继续、取消和重试入口。
7. 用户需要播放时安装 QQ 音乐浏览器扩展，并在扩展与本机 API 之间完成一次性配对。

### 5.2 自然语言选歌

1. 用户输入一段整体感觉。
2. 系统建立搜索会话并解析内部意图。
3. 系统对当前“喜欢”中所有画像可用歌曲进行全量评分。
4. 靠近均衡阈值的候选进入边界复核。
5. 所有通过阈值或复核的歌曲组成候选集合；无通过歌曲时返回 0。
6. 默认按匹配度展示，用户可切换情绪曲线或随机排序。
7. 用户可试听、删除、拖动、找相似，或继续追加“再有律动一点”“不要英文歌”等会话要求。
8. 用户点击播放后，系统重新校验成员和可播放状态，再提交队列。

### 5.3 播放

1. 播放连接器确认 QQ 音乐页面在线、已登录并已配对。
2. 连接器按队列定位歌曲，并报告成功、不可播放、未找到或页面状态异常。
3. 播放状态同步回 MoodMusic，包括当前项、进度、暂停和切歌。
4. 当最后一首自然结束时，连接器阻止平台自动续播并停止。
5. 队列播放中如果用户取消喜欢，当前队列不被中途破坏；下次搜索不再包含该歌曲。

### 5.4 外部相似歌曲

1. 用户从本次描述、某首候选或候选集合点击“更多风格类似的歌”。
2. 后端执行真实联网搜索，不依赖模型记忆直接生成歌名。
3. 结果通过可用的曲库搜索校验歌名、歌手、版本和可用性。
4. 外部建议单独展示，可试听、在 QQ 音乐中打开以便用户人工加入喜欢，或由用户明确手动加入当前队列。
5. 手动加入当前队列的歌曲必须标记为“外部推荐”，不能伪装成原始喜欢成员。

## 6 功能需求

### FR 01 音乐库同步

- 后端只读数据适配器使用已验证的 Cookie 获取用户当前“喜欢”歌曲身份与基础元数据。
- 适配器使用分页同步并提供断点、重试和幂等导入；CSV 导入保留为回退。
- 使用 `provider + sourceTrackId` 去重；ID 缺失时只允许进入待确认区，不能依据歌名强行合并。
- 取消喜欢保留最小历史标记，不立即删除相关搜索历史。
- 支持 CSV 人工导入作为数据适配器不可用时的回退方案。

### FR 02 歌曲画像

- 每首歌必须具有身份、语言与人声、曲风、声学、情绪、场景、歌词语义、编曲感知、运动适配、语义描述和治理字段。
- 字段同时保存值、来源、置信度、模型版本、画像版本和更新时间。
- 用户可以编辑字段并锁定；重新分析不得覆盖锁定字段。
- 画像失败可以按批次退避重试并从 checkpoint 恢复。
- 新增喜欢只执行增量画像；模型或画像模板变更必须产生新版本。

### FR 03 语义选歌

- 解析用户原始描述和当前会话追加要求。
- 使用语义向量、连续特征和硬边界共同评分，不能只依赖单个标签。
- 对全部已完成画像的当前喜欢成员计算得分，不使用固定 Top-K 截断。
- 对阈值附近候选执行结构化 yes/no 边界复核。
- 主结果仅包含通过均衡匹配标准的歌曲。

### FR 04 候选编辑与排序

- 删除、跳过、拖动和追加要求只写入当前搜索会话。
- 支持对任意候选歌曲执行“找相似”。
- 匹配度排序按综合匹配分从高到低。
- 情绪曲线排序依据查询意图生成平滑的能量和情绪走势，并记录可复现参数。
- 随机排序只在当前匹配集合内洗牌，保存随机种子以便历史回放。

### FR 05 队列与历史

- 搜索结果默认是临时队列。
- 保存搜索原文、追加要求、候选集合、人工调整、排序模式和模型/画像版本。
- 用户明确点击导出时生成可恢复的歌单清单；首版不通过私有接口创建或修改 QQ 音乐正式歌单。
- 历史页面可以重建当时队列，但播放前仍使用当前喜欢状态与可播放性校验。

### FR 06 QQ 音乐接入

- 设置页支持写入、替换、验证和清除 QQ 音乐 Cookie，成功响应永不回显原值。
- Cookie 只进入当前 Windows 用户的操作系统凭据存储，不进入业务数据库、Git、日志、诊断包、前端持久化或模型请求。
- 只读数据适配器负责登录状态和“我喜欢”分页同步；接口参数和原始响应不得进入核心业务模型。
- 播放扩展支持一次性配对、断线重连、能力协商和版本上报，只操作用户当前页面可见、可交互的播放内容。
- 页面结构不兼容时必须停止自动操作并给出诊断，不得盲目点击。
- 提供歌曲定位、队列播放、播放状态、暂停、继续、上一首、下一首和停止能力；实际能力通过协商返回。
- 首版不提供二维码登录、QQ 音乐写操作、播放 URL 提取、下载、代理、缓存或解密。

### FR 07 模型与费用

- 聊天模型、Embedding 模型和外部搜索提供方分别配置。
- 支持 OpenAI 聊天与 Embedding；聊天层预留 DeepSeek 适配器，但不得假设其提供同等 Embedding 或联网搜索能力。
- 提供连接测试、超时、并发和批量设置。
- 初始化前显示估算用量；可配置预算提醒和硬上限，默认关闭硬上限。
- 所有请求记录去敏后的提供方、模型、耗时、用量和错误类型。

## 7 非功能需求

### 7.1 可靠性

- 同一导入批次和同一队列提交支持幂等重试。
- API、模型或连接器故障不应破坏已有歌曲库和历史记录。
- 画像任务重启后可以从最后一个已持久化 checkpoint 恢复。

### 7.2 性能

- 对约一千至数千首个人曲库优先保证结果完整和可解释的内部证据，不为过早优化牺牲召回。
- 普通搜索请求应流式反馈阶段状态，长任务不得阻塞 API 健康检查和已有播放控制。

### 7.3 隐私与安全

- QQ 密码永不进入应用；Cookie 只保存在操作系统凭据存储中，不进入业务数据库、日志、前端持久化或模型请求；受保护播放 URL 不被提取或保存。
- API Key 不写入仓库、前端 bundle、普通配置文件或日志。
- 音频不得上传给云端模型；只有用户明确拥有处理权并且浏览器正常授权可播放时，才允许在内存中做临时分析。

### 7.4 可维护性

- QQ 音乐只读数据适配器、播放连接器与核心业务分别通过内部 Provider 接口和版本化消息契约隔离。
- 页面选择器集中管理并具备兼容性探测和回归样本。
- 模型输出必须经过 schema 验证，解析失败不得污染正式画像。

## 8 成功指标与验收标准

首版发布前至少完成以下验证：

- 使用不少于 30 条代表性自然语言提示进行人工听感评测。
- 在约定评测集上，主候选人工准确率目标不低于 85%。
- “不要太悲伤”等严重反向情绪误判为 0。
- 主候选全部来自搜索时刻的“喜欢”集合，外部建议自动混入次数为 0。
- 所有通过均衡阈值的歌曲都进入候选集合，合法支持 0 结果。
- 三种排序都只重排同一候选集合，不暗中增加或删除歌曲。
- 同步重复、删除和增量新增正确；任务暂停、恢复和重试可用。
- 歌曲集合、预览顺序与提交播放顺序一致；最后一首结束后停止。
- Cookie 缺失或过期、QQ 私有接口变化、QQ 页面不兼容、播放连接器离线、模型超时或配额不足时均能安全降级。
- Cookie 设置、验证、替换和清除流程通过；日志、数据库、诊断包和前端存储扫描中没有 API Key、QQ Cookie、受保护播放 URL 或原始音频。

## 9 开放问题

以下问题必须通过原型验证后进入 ADR，不在实现中隐式决定：

- 当前 Cookie 字段和 QQ 音乐只读接口能否稳定完成一千首以上“我喜欢”的分页同步。
- 网页播放器能否通过页面可见操作可靠构造临时队列并阻止自动续播。
- 数据适配器和网页播放器分别能取得哪些可靠的歌曲身份字段，二者能否稳定映射同一歌曲。
- 没有授权音频分析时，BPM 和声学字段的合法数据源与覆盖率。
- Cookie 平均有效期、失效错误特征和重新粘贴体验能否满足个人日常使用。
