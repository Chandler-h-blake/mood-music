# ADR 001 采用独立应用形态

- 状态：Accepted
- 日期：2026-09-08
- 决策者：项目所有者

## 背景

最初方案要求把入口和页面直接加入固定版本 QQ 音乐桌面客户端，并通过进程内原生插件访问“喜欢”和播放队列。该方案能提供最原生的视觉体验，但需要固定 32 位客户端、维护内部 ABI、符号签名、注入、GF 界面资源和崩溃隔离。它与当前以 Web 全栈和 AI 应用工程为主的学习路线不一致，也会把大量精力放在客户端逆向和版本兼容上。

项目所有者已经接受：产品可以是自己开发的网站或软件，不再要求代码直接嵌入 QQ 音乐桌面程序。

## 决策

首版采用独立 Web 应用和本机 API 服务。产品自身负责歌曲库、画像、AI 匹配、候选编辑、历史和外部发现；QQ 音乐只通过独立连接器提供可获得的同步与播放能力。

当前仓库不包含 C++、DLL 注入、Native Hook、GF/XML 资源替换或固定 QQ 音乐二进制哈希。原计划书继续作为历史输入保留，已确认的业务规则迁移到当前 PRD。

## 影响

正面影响：

- 主技术栈与 TypeScript、Next.js、Python、FastAPI、PostgreSQL 和 AI 学习路线一致。
- AI 核心与具体音乐平台解耦，QQ 连接方式失效时不会丢失歌曲画像和搜索能力。
- QQ 音乐客户端升级不会直接导致进程崩溃或无法启动。
- 产品页面、测试、部署和调试更容易形成公开可展示的工程作品。

代价：

- 无法承诺完全等同于 QQ 音乐桌面原生页面的体验。
- 普通网站无法直接读取另一个站点或控制桌面软件，仍需浏览器扩展或本地助手。
- 保存正式 QQ 音乐歌单和构造播放队列的能力取决于获准使用的网页操作路径。

## 退出方案

如果未来获得官方开放接口，可新增官方 Provider 实现而不改变核心域模型。如果网页连接器不可行，可以退回手动导入和跳转播放，或另立 ADR 评估 Windows 本地助手；不得在本 ADR 下悄悄恢复进程注入方案。
